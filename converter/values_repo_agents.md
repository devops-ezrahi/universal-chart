# AGENTS.md

This is a **gitops values repo**: values files only, no templates. Argo CD
deploys every release here with the **universal Helm chart**. The chart's own
repo holds the full, version-matched documentation. You MUST read it before
any task that writes, changes, reviews or explains values.

## Step 1: find the chart version this repo deploys

In `rootApplicationSet.yaml`:
- `chartRepoURL` / `chartRevision` helm parameters, if present;
- otherwise the chart source's `repoURL` / `targetRevision` in the same file
  (the universal chart and ms-applicationSet live in one repo).

If there is no `rootApplicationSet.yaml`, use the values this file was
generated with: `__CHART_REPO_URL__` at `__CHART_REVISION__`.

Then use the first source that works:

1. **A local clone.** Look for `../universal-chart` (or any sibling folder whose
   git remote is the chart's repo URL). If it exists, **update it first** and
   check out the deployed revision:
   ```bash
   git -C ../universal-chart fetch --tags --prune origin
   git -C ../universal-chart checkout --detach <chartRevision>   # a tag, or origin/<branch> for a branch
   ```
   If it has local changes, don't touch it. Tell the user and use source 2.
2. **The Bitbucket MCP.** Read the chart's files at `<chartRevision>` directly.
   This is always current. You can't render without a clone, so say your
   answer is unverified.
3. **Neither works.** Stop and ask the user: "Can I clone `<chartRepoURL>` to
   `../universal-chart`? I'll give better, verified answers with it." If yes,
   clone it and go to source 1. If no, answer from this repo alone, and say that
   the answer is based on this repo's values only.

Before each task, confirm the checkout is at `<chartRevision>`. The value in
`rootApplicationSet.yaml` changes on chart upgrades.

## Step 2: read the chart's docs (from the clone or through MCP)

3. `docs/ai/gitops-and-converter.md`: this repo's layout and the Argo CD wiring.

If that revision has no `docs/ai/` (older than the docs), use its
`templates/` and `values.yaml` as the reference. Say that you did.

## This repo's layout

```
base/<release>.yaml                 shared by EVERY namespace (prod included)
<ns>/defaults.yaml                  every release in one namespace
<ns>/values/<release>.yaml          one namespace only: image tag, replicas, differences
```

Layered lowest → highest: `base` → `defaults` → `values`.
Put a change in the narrowest file that covers it. If it goes in `base/`, say
that it changes prod too.

## Rules that apply even before you read the docs

- Collections are **maps keyed by name**, not lists (`env`, `ports`, `volumes`, ...).
  `volumeMounts` is the exception.
- Features are **off by default** (`service.enabled`, `serviceAccount.create`, ...).
- Never invent a key. Find it in the chart first.

## Verify every change

```bash
helm template <release> ../universal-chart -n <ns> \
  -f base/<release>.yaml -f <ns>/defaults.yaml -f <ns>/values/<release>.yaml
```

Read the output, then check that `git diff` touches only the intended files.
If you couldn't render, say so.
