ADDITIONAL CONTEXT / CLUES:
- TWO INDEPENDENT DEFECTS, BOTH MUST BE FIXED — capturing the labels without rendering them changes nothing, and vice versa:
  1. CONVERTER: handle_cronjob() at convert_to_universal_chart.py:1800-1804 must extract spec.jobTemplate.spec.template.metadata.labels into a podLabels key. handle_workload() already does exactly this at line 982 — copy that pattern. handle_job() has the same gap.
  2. TEMPLATE: the CronJob pod template renders only selectorLabels (app.name + app.instance). It needs an objectLabels/podLabels merge block.
- The 5 lost labels per CronJob are consistently {critical, environment, operational, operationalPurpose, team} — governance/ownership metadata used for cost allocation, alert routing and environment filtering.
- THE PRIORITY TABLE FLAGS A REAL RUNTIME RISK, not just metadata loss: "Sidecar injection could crash CronJobs". Pod-template labels are what admission webhooks and sidecar injectors match on. A CronJob pod that loses its labels may miss an injection it depends on — or receive one it should have been excluded from. Verify what selects on these labels before downgrading this to cosmetic.
