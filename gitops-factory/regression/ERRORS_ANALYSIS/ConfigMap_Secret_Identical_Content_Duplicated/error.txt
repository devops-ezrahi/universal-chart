"ConfigMap Rename - You Were Right, It IS a Real Collision
Three separate microservice releases share the same ConfigMap name zookeeper-config:
Release | Workload | ConfigMap name in raw
zookeeper | StatefulSet | zookeeper-config
zookeeper-zoonav | Deployment | zookeeper-config
zookeeper-zbs | Deployment | zookeeper-config

The data is identical (same MD5 hash) - it's the same ZK config. But they are deployed as three separate releases in the same namespace. Without the rename, all three releases would try to create a ConfigMap with the same name and the last one to apply would overwrite the others.

Why the converter renamed it: The collision resolver (convert_to_universal_chart.py:399) picks the first claimant as the "owner" and renames the rest to {owner}-{name}. So one release keeps zookeeper-config, and the others become zookeeper-zoonav-zookeeper-config, zookeeper-zbs-zookeeper-config.

The volume references are updated consistently, so within each release:
- zookeeper-zoonav release creates ConfigMap zookeeper-zoonav-zookeeper-config + Deployment volume ref zookeeper-zoonav-zookeeper-config
- Both match, so it works

BUT: In the original OpenShift cluster, there was only ONE ConfigMap named zookeeper-config shared by all workloads. The converter split it into three separate ConfigMaps. This means:
- Original: 1 ConfigMap, 3 workloads read from it
- Converted: 3 ConfigMaps (if content was identical, could be shared again but isn't)"

"ConfigMap zookeeper-config Sharing Bug - Analysis
What happened:
- zookeeper-zbs got owner of zookeeper-config (processed first alphabetically)
- zookeeper-zoonav renamed its copy -> zookeeper-zoonav-zookeeper-config
- zookeeper (the StatefulSet) renamed its copy -> zookeeper-zookeeper-config
Result in the namespace: 3 ConfigMaps with identical content instead of 1 shared ConfigMap.
Why the converter missed sharing it: Only ConfigMaps that appear in shared.yaml get promoted to the shared release. zookeeper-config is NOT in shared.yaml - it only appears in the 3 zookeeper-specific files. So the converter treats them as independent collisions rather than shared resources.
Two problems:
1. Wrong: 3 redundant ConfigMaps instead of 1
2. Volume references broken: zookeeper release's volume points to zookeeper-zookeeper-config, but that ConfigMap may be rendered by the wrong release or not at all (depends on which release actually creates it)"

"The claim() method at line 384-405 only returns "reference_shared" when the existing owner is "_shared" (i.e., declared in shared.yaml). When two regular microservices collide, it doesn't check whether the content is identical - it just renames the second one. The identical content note in the warning is informational only, not a shared reference.
The logic is:
1. shared.yaml declares it first -> owner = "_shared" -> other microservices get "reference_shared" (shared)
2. Microservice A declares it first -> owner = "A" -> Microservice B gets "renamed" even if identical
The bug: When content is identical, the second microservice should get the same treatment as reference_shared - do not copy and reference the first owner's version. Instead it creates a duplicate with a new name.
Want me to plan a fix that checks existing["hash"] == content_h and triggers "reference_shared" behavior in that case?"

"How should the converter handle identical ConfigMaps/Secrets across microservices in the same namespace? HOW IT HANDLES NOW
1. First microservice to claim the name keeps the original name - action "own"
2. Second (and later) microservices that claim the same name get renamed - action "renamed" to <owner>-<name>
3. All volume/env references in the renamed microservice are updated to point to <owner>-<name>
4. The original name stays unchanged for the first winner
The result is:
- Two separate Secret objects in the rendered output (one original, one prefixed)
- Both are consistent internally (references point to the right name)
- But this creates unnecessary duplicates - two Secret objects instead of one shared reference
This is by design. The converter doesn't auto-share because it can't know if the original cluster actually had a shared Secret or two separate ones that happened to have identical content. It takes the safe path: rename them so both microservices have their own independent copy.
The "reference_shared" behavior only triggers when the resource is in shared.yaml (line 385: if existing["owner"] == "_shared"), meaning the operator intentionally declared it as shared."
