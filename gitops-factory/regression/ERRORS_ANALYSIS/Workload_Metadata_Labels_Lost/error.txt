error: Raw metadata.labels are lost for nearly all resource types — the converter never stores them and the chart templates never render them (~634 label fields / 3,087 lost labels).

EXACT TEXT EXTRACTED FROM IMAGES:
"Fidelity Error Analysis - Why Each Error Occurs
1. Lost metadata.labels (~634 fields)
What happens: Raw manifests have labels like app: test-jenkins, argocd.argoproj.io/trace-id: <uuid>, version: 2.0.0, etc. on Deployment, StatefulSet, DaemonSet, CronJob, Job, Service, Route, PVC, ConfigMap, Secret, SecretStore, ExternalSecret, NetworkPolicy, RBAC, ServiceAccount.
Why: The converter has a split design flaw:
 - handle_workload stores labels at lines 796-797, but ONLY for ConfigMap/Secret handlers do they actually appear in the rendered templates.
 - For workload handlers, labels are stored but the corresponding templates (deployment.yaml, statefulset.yaml, daemonset.yaml) ONLY render {{- include "universal-chart.labels" $spec }} (lines 5-8, 7-8, 7-8), which produces only 3 auto-generated labels: app.kubernetes.io/name, app.kubernetes.io/instance, app.kubernetes.io/managed-by.
 - Handlers for CronJob, Job, Service, Route, PVC, SecretStore, ExternalSecret, NetworkPolicy, Role, RoleBinding, ServiceAccount NEVER capture labels at all.
 - The chart templates for all of these similarly ONLY render the auto-generated helper labels.
Summary: The converter doesn't store raw labels for most resource types, and the templates don't have a {{- with $spec.labels }} block to render them if they were stored."

"# deployment.yaml line 7-8:
metadata:
  labels:
    {{- include "universal-chart.labels" . | nindent 4 }}
# <- No second block like {{- with .Values.workloadLabels }}
While ConfigMap/Service templates do have a secondary {{- with $spec.labels }} block"

"Summary
correct.py output -> All labels present
convert_to_universal_chart.py -> Drops workload metadata.labels (only captures pod template labels)
values.yaml -> commonLabels: {} (empty, never populated)
deployment.yaml -> Only renders 5 Helm identity labels via _helpers.tpl
helm template output -> 3,087 LOST labels"

"What convert_to_universal_chart.py does (line 720-725):
# Reads pod template labels, removes identity ones
pod_labels = {
    k: v for k, v in pod_meta.get("labels").items()   # <- this is spec.template.metadata.labels
    if k not in ("pod-template-hash", "app.kubernetes.io/name", "app.kubernetes.io/instance", ...)
}
v["podLabels"] = pod_labels   # -> stores: team, critical, environment, part-of, argocd...
Then commonLabels stays {} empty. The workload's own metadata.labels is never read."

"Why this is a corruption, not just a 'loss'
The podLabels approach works for pod template labels because app.kubernetes.io/name and ... are the ones Helm needs to control. The converter strips those 4 identity labels from pod. Custom labels survive through podLabels.
But commonLabels is the equivalent mechanism for resource-level labels, and the workload's metadata.labels only gets Helm's identity labels, losing all 3087 custom labels.

Why other resource types are affected differently
ConfigMap - converter copies metadata.labels to entry["labels"], template has {{- with ...}} -> Labels survive [OK]
Service - same as ConfigMap -> Labels survive [OK]
Secret - same pattern -> Labels survive [OK]
Deployment/StatefulSet/DaemonSet - no equivalent code -> Labels lost [X]"
