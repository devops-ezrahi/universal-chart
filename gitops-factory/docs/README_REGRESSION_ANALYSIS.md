## 2. Root-cause analysis: why the recurring ones recurred

Eight causes. None of them is "someone reverted the fix".

### RC-1 — The validation corpus exercises none of these defects

`namespaces-showcase/` is what every previous-round fix was validated against,
and what the fidelity report is generated from. Its complete inventory:

```
20 ServiceAccount  19 Service  17 ConfigMap  10 RoleBinding  10 Role
 7 Deployment       4 StatefulSet  4 Secret   4 PodDisruptionBudget
 4 NetworkPolicy    4 HorizontalPodAutoscaler  4 DaemonSet  3 Ingress
 2 PersistentVolumeClaim  2 Job  2 CronJob  2 ClusterRoleBinding
 2 ClusterRole      1 SecretStore  1 ExternalSecret
```

**There are zero Routes.** There are also zero occurrences of every field the
new report is about:

```
minReadySeconds                        0 files
enableServiceLinks                     0
shareProcessNamespace                  0
allocateLoadBalancerNodePorts          0
persistentVolumeClaimRetentionPolicy   0
parallelism                            0
checksum/                              0
ownerReferences                        0
```

Nor any non-ASCII byte, any Sensor/EventSource, or any volumeClaimTemplate
carrying labels.

A full converter run on this corpus today reports:

```
122 objects matched (28 legitimately relocated).
No fidelity issues found.
```

The previous round read that zero as *"no regression"*. It is not. It is
**no coverage**. The single largest defect in the new report — 613–705 lost
Route labels — cannot be seen by this corpus at all, because the corpus has no
Routes. Every recurring defect in §1a lives inside that blind spot.

`StatefulSet_PVC_Retention_Policy_Lost/STATUS.md` §6 says exactly this about its
own defect ("the showcase data does not exercise this defect") and even names
the consequence — "The committed fidelity report shows 0 for this defect class
both before and after, because there is no raw input carrying the field to
lose." The observation was correct and was never generalised beyond that one
folder.

### RC-2 — Fixtures were built per-folder, never folded into the corpus

Each previous folder built a fixture under its own `test/fixture/` to prove its
fix in isolation. That is correct for proving the fix and useless for detecting
its loss. Nothing added those fixtures to `namespaces-showcase/`, so the next
full run still cannot see the field, and no future run can detect it going
missing again.

The side effect is documented in the same STATUS file §7: the fixtures were
visible enough to the stale-output scanner that `NON_NAMESPACE_OUTPUT_DIRS` had
to be taught to ignore `ERRORS_ANALYSIS` entirely. The fixtures were made
*invisible to the tooling* rather than *visible to the corpus*.

### RC-3 — One outright half-fix: the comment was written, the code was not

`convert_to_universal_chart.py:1066` onward:

```python
def build_route_entry(doc: dict, ctx: MicroserviceContext) -> dict:
    # labels handled at the end of this function via raw_labels(doc)
    ...
    return entry          # <- raw_labels() is never called
```

`grep -n "raw_labels("` returns 20 hits across 14 handlers — Service, ConfigMap,
Secret, ExternalSecret, PVC, NetworkPolicy, Role, RoleBinding, ServiceAccount,
ServiceMonitor, CronJob, Job, workloads, cluster-scoped. Line 1067 is the
**only** hit that is a comment rather than a call.

`git diff` on the working tree shows that comment being *added* by the same
change that added the real `entry["labels"] = raw_labels(doc)` line to every
other handler. The Route handler received the note and not the line.

The template side is complete — `templates/route.yaml` and
`templates/routes.yaml` both render
`include "universal-chart.objectLabels" (dict "root" $ "own" .labels)`. The
chart is waiting for a value the converter never produces.

**This is the one place where a previous fix is genuinely, provably incomplete
rather than merely unexercised.** It accounts for the largest single error class
in the new report.

### RC-4 — The architecture is an allow-list, so every new field is a new bug

The converter captures fields by explicit enumeration:

- `handle_workload` — a scalar whitelist (`terminationGracePeriodSeconds`,
  `hostNetwork`, `hostIPC`, `hostPID`, `shareProcessNamespace`,
  `priorityClassName`, `runtimeClassName`, `schedulerName`, `dnsPolicy`,
  `restartPolicy`) plus a truthy whitelist. `minReadySeconds` and
  `enableServiceLinks` are in neither.
- `build_service_entry` — field by field. `appProtocol`, `sessionAffinity` and
  `externalTrafficPolicy` were each added by a previous folder.
  `allocateLoadBalancerNodePorts` was never named, so it is lost.
- `handle_cronjob` — `jobTemplate.spec` keys `backoffLimit`,
  `activeDeadlineSeconds`, `ttlSecondsAfterFinished`. `parallelism` is not
  named.
- the volumeClaimTemplates loop — `accessModes`, `size`, `storageClassName`,
  `volumeMode`. No `metadata.labels`.
- `raw_labels()` — called by hand at 14 sites rather than at one shared seam.

Under an allow-list, *"we fixed field X"* never generalises to field Y. The
previous round fixed 34 defects. This round found the next 12 fields the
whitelists do not name. A third round would find the next 12 after that.
**This is the mechanism that guarantees recurrence, and it is the only one worth
fixing structurally.**

### RC-5 — Two documents, two corpora, incomparable counts

`Summary_Vs_Report_Data_Mismatch` is right that the summary and
`fidelity_report.txt` describe different runs, and right that this invalidates
planning built on the summary. It offers two readings — "the summary is older
and those 8 were fixed" versus "different input set, still live" — and cannot
choose between them.

§0 chooses. The report is the **current converter on a larger corpus**, so the
eight error types absent from the report (`imagePullSecrets`, ServiceAccount
`secrets`, `containers[0].resources`, `progressDeadlineSeconds`,
`securityContext`, `sessionAffinity`, Job/CronJob misc, `volumeMounts` subPath)
are absent because **they were genuinely fixed last round** — every one has a
`STATUS.md` marked FIXED and the code is still present. That is reading (1), and
it is good news that was simply never recorded.

The same logic dissolves `Extra_And_Relocated_Objects`' "0 vs 90"
contradiction: 0 is the post-fix run on `namespaces-showcase`, 90 is the
`rakia-*` corpus. Both are true of their own run.

### RC-6 — No idempotence guard in the collision renamer

`NamespaceRegistry.claim`, line 502:

```python
new_name = f"{owner}-{name}"
```

Unconditional. When `owner == "interconn-kafka-kafbat"` and
`name == "interconn-kafka-kafbat"`, the result is
`interconn-kafka-kafbat-interconn-kafka-kafbat` — precisely the string the new
report quotes.

The previous round fixed the *CronJob/Job* doubling (`short_subresource_name`,
commit `d85496a`, "chart: stop doubling CronJob/Job names against their own
release name") by making the subresource key strictly the raw name. It did not
touch this function, which is a different code path serving every other kind.
`Argo_Events_Sensor_Double_Prefix` is the same line reached by a third kind. The
new report's own instruction is to fix it once: "Investigate the naming logic
once, then update all three. Do not fix them independently — you will make three
inconsistent changes to the same code path."

### RC-7 — `ports_list_to_map` keys on port number; the checker keys on number + protocol

The two halves of the pipeline disagree about what identifies an unnamed port.

`ports_list_to_map` (line 645):

```python
out[f"port-{p['containerPort']}"] = entry      # key = number only
```

`_item_name` (line 3013), whose own docstring states the rule:

```python
return f"#port:{item['containerPort']}/{item.get('protocol', 'TCP')}"
# "a container may not declare the same containerPort/protocol pair twice"
```

The checker is right: `9125/TCP` and `9125/UDP` on one container are legal
Kubernetes and are two distinct ports. The converter's key ignores protocol, so
both collapse onto `port-9125` and the second silently overwrites the first.
`Missing_Container_Port_9125` records its root cause as "UNKNOWN"; this is the
leading candidate, and 9125 TCP+UDP is the canonical statsd-exporter pair. To be
confirmed by test in Phase 2 rather than asserted here.

### RC-8 — `helm template` output is decoded with the Windows ANSI codepage

Not a recurrence — a new defect — but the root cause is already located, so it
belongs with the rest.

`helm_template()`, line 2661:

```python
result = subprocess.run(cmd, capture_output=True, text=True)
```

`text=True` with no `encoding=` decodes the child's stdout using
`locale.getpreferredencoding()`, which on this machine is cp1252. Helm emits
UTF-8. Decoding UTF-8 bytes as cp1252 is precisely the mojibake in the report:
`Ľ` is U+013D → UTF-8 `0xC4 0xBD` → cp1252 `Ä¾`; the em-dash is U+2014 → UTF-8
`0xE2 0x80 0x94` → cp1252 `â€"`. Both signatures match exactly.

Every `read_text` / `write_text` in the converter already passes
`encoding="utf-8"`. This one call site does not, and it is the only place the
pipeline crosses a process boundary. `UTF8_Encoding_Corruption_In_ConfigMap_Data`
names the fix pattern already present in this repo: `run_all.py` calls
`subprocess.run(..., encoding="utf-8", errors="replace")`.

## 4. Strategic plan — how to fix these permanently

The word that matters is *permanently*. Fixing the 26 folders one at a time
reproduces the previous round exactly: 26 correct fixes, a corpus that still
cannot see any of them, and a third analysis in six months. The plan below fixes
the folders **and** closes the mechanism.

### Principle 1 — Every fix lands in the shared corpus, not only in its own `test/`

For each folder whose defect is invisible to `namespaces-showcase`, add the
smallest raw manifest that exercises it **to `namespaces-showcase/` itself**,
not only to that folder's `test/fixture/`. A defect the corpus cannot express is
a defect the next run cannot catch.

This round needs at least: one Route carrying governance labels; one CronJob
with pod-template labels; one Deployment with `minReadySeconds` and
`enableServiceLinks: false`; one LoadBalancer Service with
`allocateLoadBalancerNodePorts`; one StatefulSet whose volumeClaimTemplate
carries labels; one ConfigMap containing non-ASCII text.

The per-folder `test/` still gets its focused unit test. The corpus gets the
regression tripwire. The two are not substitutes for each other.

### Principle 2 — Convert allow-lists into deny-lists where the field set is open

RC-4 is the recurrence engine. Where a whitelist enumerates fields of an
open-ended Kubernetes object, invert it: copy everything, subtract the small
closed set the chart owns or that the API server populates. `raw_labels()`
already demonstrates the shape — it copies all labels and subtracts
`CHART_OWNED_LABELS`.

Where inverting is too large a change to make inside one defect's scope, the
minimum acceptable alternative is a **test that enumerates the whitelist and
fails when a known Kubernetes field of that object is absent from it** — so the
next missing field surfaces as a red test rather than a third analysis round.

### Principle 3 — Fix at the seam, once, for all kinds

- `raw_labels()` is called at 14 sites by hand; R1 exists because the 15th was
  missed. A single labelling seam every handler passes through removes the class.
- `NamespaceRegistry.claim`'s prefix (RC-6) serves every kind. One idempotence
  guard there is expected to fix `Helm_Naming_Prefix_Collisions` **and**
  `Argo_Events_Sensor_Double_Prefix`.
- `ports_list_to_map`'s key (RC-7) must adopt the checker's identity
  (number + protocol), not the reverse — the checker's is the identity
  Kubernetes itself uses.

### Principle 4 — Suppress only against a verified condition, never against a bucket

`K8s_Runtime_Defaults_Benign_Suppress` is worth ~930 of 1,314 errors and is the
highest-leverage item in the batch. It is also the most dangerous, because three
real losses were swept into it purely by adjacency in the pod spec:

- `minReadySeconds` — the Kubernetes default is **0**, not 10. An explicit 10 is
  a deliberate rollout-safety setting. Preserve it.
- volumeClaimTemplate **labels** — suppress the VCT *runtime* keys (`status`,
  `kind`, `apiVersion`, `creationTimestamp`); never the whole subtree.
- `allocateLoadBalancerNodePorts` — 62 benign Redis announce Services, 3 real
  LoadBalancers. Scope the rule; do not blanket the path.

And one whose stated reason is factually wrong even though the verdict is
probably right: `enableServiceLinks` — the Kubernetes default is **true**, so an
explicit `false` is a deliberate opt-out, not a redundant restatement of the
default. Do not let the wrong premise carry the decision.

Rule for the whole programme: **write each rule against the specific key, verify
the stated condition once, and record the verification in that folder's
STATUS.md.** Suppression is cheap to apply and expensive to discover you were
wrong about.

### Principle 5 — Settle the disputed verdicts before writing code

Three folders are decisions, not defects, and coding before deciding produces
churn:

- **`Route_Governance_Labels_Lost`** — the report gives three incompatible
  instructions (fix / suppress / "not suppressed by design"). **Decision: FIX.**
  The chart already renders `.labels` on both Route templates; the converter
  simply never fills it, so the fix is one line at the seam that was documented
  and not written. Suppressing would hide a real loss the report's own priority
  table rates P1. The single genuine exception is
  `argocd.argoproj.io/instance` (92), which ArgoCD writes at sync time — that
  row alone is legitimately suppressible.
- **`Secret_ConfigMap_Rename_Reference_Inconsistency`** — decide by rendering
  each affected release and checking that every reference
  (`volumes[*].secret.secretName`, `volumes[*].configMap.name`,
  `env[*].valueFrom.secretKeyRef.name`, `envFrom`) resolves to an object the
  same release actually creates. All resolve ⇒ cosmetic, suppress. Any dangles
  ⇒ P0, the pod will not start.
- **`Extra_And_Relocated_Objects`** — reconcile 0 vs 90 by establishing which
  run each belongs to, then, for each object rendered by nothing, search the
  render for a same-kind object with matching content under a different name.
  Found ⇒ rename ⇒ benign. Not found ⇒ genuinely lost ⇒ P0.

### Principle 6 — One authoritative run

Per RC-5, rebuild the summary **from** `fidelity_report.txt`, never alongside
it. The report is generated output and is authoritative; the hand-maintained
summary is not. Every count in this batch that "moved" should be re-measured on
one known input before it is planned against.

## 5. What this analysis could not determine

Stated plainly rather than glossed:

- **Whether the `rakia-*` manifests behave as predicted.** They are not in this
  repo. Every root cause above is proven against the code and will be proven
  against a fixture; none can be proven against the actual input behind the
  1,314-line report.
- **The true value of any count.** Per RC-5, no count in this batch is reliable
  until one authoritative run exists. Counts are used here to rank, never to
  conclude.
- **`Sanitizer_Drops_Unparsed_Lines`' three lines.** They exist only in the
  internal report of a run this repo does not hold. The parser gap can be
  characterised; those three specific lines cannot be read.
