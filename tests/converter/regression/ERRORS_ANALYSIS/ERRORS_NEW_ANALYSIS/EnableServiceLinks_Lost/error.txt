- ONE FACTUAL CORRECTION WORTH KNOWING, because it inverts the usual reasoning: the Kubernetes default for enableServiceLinks is TRUE, not false. An explicit `enableServiceLinks: false` is therefore a DELIBERATE OPT-OUT, not a redundant restatement of the default — and dropping it means the rendered pods get service-link environment variables injected that the raw manifests explicitly disabled.
- WHY IT USUALLY STILL DOES NOT MATTER: service links inject a set of {SVCNAME}_SERVICE_HOST / _PORT environment variables for every Service in the namespace. Most applications ignore them. Teams disable them for two reasons — to reduce pod startup env bloat in namespaces with many Services, and because an injected variable name can collide with an application's own env var and silently override it.
- THEREFORE VERIFY BEFORE SUPPRESSING: for the affected workloads, check whether any container env var name could collide with a {SERVICE}_SERVICE_HOST/_PORT pattern from a Service in the same namespace. If one does, re-enabling service links overrides the application's own configuration at runtime — a real and very hard-to-diagnose bug. If none does, suppress freely.
- The report's stated reasoning ("false is the K8s default") is wrong on the facts but likely right on the outcome. Do not let the wrong premise carry the decision — confirm the collision check.
