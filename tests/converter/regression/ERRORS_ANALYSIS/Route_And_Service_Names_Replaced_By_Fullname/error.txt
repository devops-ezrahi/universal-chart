CONCRETE EXAMPLE (verbatim):
"Concrete Example: control-station-client
Raw manifest (namespaces/interconn/control-station-client.yaml):
# Service in raw:
  name: control-station-client-service        # <- original name
spec:
  selector:
    app: control-station-client
    app.kubernetes.io/instance: control-station-client-interconn
    app.kubernetes.io/name: control-station-client
# Route in raw (points to the service above):
  name: control-station-client-route          # <- original name
spec:
  to:
    kind: Service
    name: control-station-client-service      # <- references the service by name

What the Helm chart renders (from service.yaml line 5 and route.yaml line 6):
# Service rendered:
  name: {{ include "universal-chart.fullname" . }}
# Route rendered:
  name: {{ include "universal-chart.fullname" $ }}
spec:
  to:
    kind: Service
    name: {{ include "universal-chart.fullname" $ }}   # -> same name as the route

So Helm renders:
# Service:
  name: control-station-client        # <- NOT "control-station-client-service"
# Route:
  name: control-station-client        # <- NOT "control-station-client-route"
spec:
  to:
    kind: Service
    name: control-station-client      # <- points to "control-station-client" (OK - matches)

The problems:
1. Raw Service name: control-station-client-service -> Rendered name: control-station-client
   - Anything referencing control-station-client-service (other config, DNS, other routes) will break
2. Raw Route name: control-station-client-route -> Rendered name: control-station-client
   - Same name collision between Service and Route
3. Raw Route to.name: control-station-client-service -> Rendered to.name: control-station-client
   - In this case the route still resolves correctly internally, but if the original name was referenced elsewhere, it's now wrong

Another example from the report - Route/interconn-kafka-kafbat (line 557):
raw    spec.to.name: 'interconn-kafka-kafbat-service'
render spec.to.name: 'interconn-kafka-kafbat'
The route now points to a service named interconn-kafka-kafbat, but the original pointed to interconn-kafka-kafbat-service - if that service still exists under the old name from a previous deployment, the route is broken (points to nothing).

Root cause: The chart uses universal-chart.fullname for ALL resource names (service, route, deployment...), dropping the original naming suffixes like -service, -route, etc. The raw manifests used distinct names per object; these names may be hardcoded in configs, other references, or DNS entries."
